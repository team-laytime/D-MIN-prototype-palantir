```bash

#    스크립트는 고치지 않고 TARGET만 바꿔 실행한다 (엔진 저장소에서)
```

데모 전에는 쓸 브라우저에서 한 번 열어 두면 된다. (`tools/real-data/build_whatif.mjs`는 지웠다)

## 2. 바뀐 것

### 후보 구성 (A 기본 · B 상황형 · C 도착 · 작업 지연 대비)

후보는 체선료 순이 아니라 **자리 고정**이다. 「최저」 표시는 실제로 가장 싼 후보에 붙는다.

| 자리 | 안 | 엔진 파라미터 |
|---|---|---|
| A | 기본 | 없음 |
| B | 상황형 — 아래 규칙으로 고른 안 하나 | 안전재고 강화 `tank.safe_min_pct 25 · safe_max_pct 75` / 보수적 풍속 기준 `weather.thresholds_ms` 중단 풍속 − 2σ / 도착 · 작업 지연 대비 절반 `shifting.vessel_buffer · work_buffer_scale 0.5` |
| C | 도착 · 작업 지연 대비 (데이터 팀 안 3) | `shifting.vessel_buffer: true` — 배마다 작업 여유(배 · 선석별) · 도착 여유(배별)만큼 간격 |

**B 고르는 규칙** (`src/lib/presets.js`, 11-26부터 이곳 한 곳)

- 탱크 등급: A 계획 재고 곡선이 마지노선 20/80%까지 2%p 안 높음 · 3.5%p 안 중간 · 5%p 안 낮음 (11-26 저녁 1 · 4 · 7에서 바꿈)
- 풍속 등급: 하역 중단 기준(3~7부두 14, 1~2부두 · 가스 18 m/s)까지 여유가 예보 오차 σ의 1배 안 높음 · 2배 안 중간 · 3배 안 낮음, **σ = 2 m/s**
- 높은 쪽 → 탱크면 안전재고 강화, 풍속이면 보수적 풍속 기준. 같으면 탱크. 둘 다 없으면 도착 · 작업 지연 대비 절반
- B 칸 머리에 고른 이유를 적는다. 다시 계산할 때는 그때의 A 계획 · 계획 조건으로 다시 고른다
- A 동점 규칙: B가 A와 체선료가 같고 탱크가 더 안전하면 A가 그 계획을 쓴다

11-09 데이터셋: A $200,972.96 · B 안전재고 강화 $206,737.10(+2.9%, 탱크 중간 23.8% · 풍속 중간 12 m/s) · C $214,194.48(+6.6%, 작업 간격 높음 리스크 0건).

### 리스크

- 후보마다 팀 리스크 모델(`berth_risk`, `POST /risks`)에 엔진 요청 · 응답을 그대로 보내 받는다. 화면에서 리스크를 세지 않는다.
- **탱크 리스크 기준을 팀 엔진 저장소에서 바꿨다**(D-MIN-optimization `ef1d026`): 계획의 안전 범위가 아니라 고정 마지노선 20/80%까지 거리 1·4·7%p(11-26 저녁 2 · 3.5 · 5%p로 바꿈, `7e18afe`). API 기준값 `tank_limit_min_pct · tank_limit_max_pct · tank_high_pct · tank_medium_pct · tank_low_pct`.
- 배별 여유를 요청에 넣었으므로 작업 간격 리스크의 필요 여유도 데이터 팀 값이다(A의 작업 간격 높음 리스크가 전보다 많다).
- 같은 요청의 리스크 결과는 브라우저 세션에 저장한다.

### 후보 비교 · 확정 화면

- 후보 비교 표: 총 체선료(바뀌면 세어 올라가고 깜빡임) · 최저안 대비 · 체선 발생 · 고정한 배 · 리스크(높음 · 중간 4건, 「전체 N건 보기」 창).
- 뺀 것: 엔진 행, 엔진 메모 문구(「탱크 재고 때문에 기다리는…」 등), 바뀐 선박 패널, 부두별 배정, 「후보 A와 부두가 다른 배」 표시, 야간 접안 표시, 회색 설명 문구.
- 배치 그림(`PlanGantt`): 시간 폭 고정 + 가로 스크롤, 체선 구간 빗금 · 체선 시간과 금액, 정박지 대기 중 체선, 고정 자물쇠, 후보를 바꾸면 막대가 미끄러져 감. 막대를 누르면 산출 근거(시각 · 체선 이유 · 그 배의 리스크 · 후보별 비교 · 「이 배정으로 고정」).
- 리스크를 누르면 리스크 근거 카드(`RiskContext`): 탱크 재고 곡선 · 마지노선 · 리스크 구간 · 관련 선박 / 작업 간격 「계획 vs 앞 배가 늦으면」 / 정박시간 여유와 체선 시작.
- 오른쪽: 조건 변경 요청 → 확정(확인할 리스크 체크 · 판단 근거) → 유사 과거 사례 → 체선 발생 선박. 오른쪽 칸은 따로 스크롤.
- 확정 뒤 화면도 같은 배치 그림. 확정 기록에 엔진 체선 시간과 작업 · 정박시간 · 호스 분리 시각을 남긴다.

### 조건 변경 요청 (받은 메일)

- 데이터셋을 불러올 때 메일 5종을 실제 선박 · 부두로 만든다(`src/lib/incidents.js`): ETA 지연 · 설비 고장 · 강풍 예보 · 우선 접안 · 탱크 운영. 왼쪽 메뉴 · 메일함 분류 이름은 「조건 변경 요청」.
- 계획 조건 화면 위 「받은 메일의 조건 변경」에서 하나씩 반영 · 반영 안 함 · 되돌리기(반영하면 다시 계산 필요).
- 후보 비교 화면 「조건 변경 요청」 패널:
  - 메일마다 '지금 + 그 조건 하나'의 A · B · C를 미리 계산해 「단독 반영 시 A $… · B $… · C $…」로 보인다(한 단계만, 데이터셋에 있으면 그것부터, 없으면 백그라운드에서).
  - 여러 개를 골라 한꺼번에 결정: 고른 것 반영, 나머지 반영 안 함. 하나 + 미리 계산 끝이면 바로 바뀌고, 여럿이면 다시 계산.
  - 결정 뒤에는 결과 요약과 「되돌리기」(결정 전 계획 조건 · 후보 · 메일 상태 · 미리 계산으로).
  - 결정 안 한 메일이 남은 채로 확정하면 한 번 더 묻고 확정 기록에 남긴다.

## 4. 11-26 데이터 팀 새 묶음 · 엔진 · 계산 방식

- **데이터 팀 11-26 묶음**(`optimizer_data_2025.zip`): 한 입항의 두 번째 이후 접안 ETA = 직전 이안(`eta_basis = DERIVED_PREV_UNBERTH`, 1년 471건), 급유선 제외(1년 199척). 1년 5,762척.
- **탱크 후보정 다시**: 새 묶음 사본 `optimizer_data_2025/optimizer_2025-01-01_tank`에 `make_tank_plan.py`. 물량 줄인 배 32척(전과 같음).
- **엔진(D-MIN-optimization)**:
  - 같은 배는 한 번에 한 선석: 같은 호출부호 · 연도 · 항차의 접안이 둘 다 계획 대상이면 순번대로, 다음 접안은 앞 접안 ETU(+ `shifting.same_vessel_gap_h`, 기본 0) 뒤에만. 앞 접안 때문에 기다리는 것은 불필요한 대기가 아니다.

### 후보 계산 순서 · 취소 (11-26 밤)

- 처음 여는 기준 시각: 후보 A가 끝나면 바로 A를 보이고(B · C 칸은 「계산 중」), A로 고른 B와 C를 이어서 계산한다. 전체 시간은 같고 첫 화면만 빨라진다.
  B · C가 끝나기 전에는 확정 · 조건 변경 결정을 막고, 「반영하면?」 미리 계산도 B · C 뒤에 시작한다.
- 엔진 호출은 작업 방식(`POST /plan-jobs` → `GET`으로 결과, 같은 요청은 Idempotency-Key로 한 작업을 같이 기다림).
  화면이 계산을 버리면(날짜 바꾸기 · 다시 계산 · 메일 결정) `DELETE`로 취소한다. 엔진(D-MIN-optimization)은 계산 중인 작업도 그 계산 프로세스를 끝내 작업자를 바로 비운다.
- 처음 계산 중에 「다시 계산」하면 처음 계산을 버리고, A가 아직 없으면 지금 계획 조건으로 A → B · C 순서로 계산한다.
- 탱크 리스크 등급(리스크 모델 · 후보 B 고르기 같은 기준): 마지노선 20/80%까지 2%p 안 높음 · 3.5%p 안 중간 · 5%p 안 낮음.
- 확정 화면: 통보 상태 패널을 빼고 확정 일정 → 모니터링 → 판단 근거 → 체선 발생 선박 순서로. 글씨 배율 `--fs` 1.2 → 1.0(화면 크기는 브라우저 확대로 맞춤).
