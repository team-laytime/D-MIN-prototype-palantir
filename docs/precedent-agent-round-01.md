# 유사 사례 첫 수집 라운드

[로드맵](precedent-agent-roadmap.md) / [데이터 정의](precedent-agent-data.md)

연간 최적화 입력에서 시연 구간을 제외하고 2025년 72시간 구간 12개에 팀 솔버를 실행했다. **A/B/C와 리스크가 모두 있는 구간은 7개, 일부 또는 전체 후보가 미산출된 구간은 5개다.** 2월 10일은 별도 파일럿이라 이 집계에서 빠져 있다.

| 결과 | 기준 날짜 |
|---|---|
| A/B/C와 리스크 확보 | 4월 3일, 5월 7일, 6월 23일, 7월 7일, 7월 27일, 9월 19일, 11월 23일 |
| 후보 미산출 포함 | 1월 11일, 4월 19일, 8월 23일, 10월 23일, 12월 23일 |

5월 7일과 7월 27일은 프로토타입 기본 한도, 나머지 10개는 탐색 한도로 실행했다. 전체 36개 슬롯 중 24개는 `FEASIBLE`, 8개는 `NO_PLAN`이었다. A안이 없으면 B 프리셋을 정할 수 없어 B 슬롯 4개는 미실행으로 보존했다. `NO_PLAN`은 이번 한도에서 배치를 찾지 못한 결과다.

12개 결과의 원본과 인덱스는 작업공간의 `output/precedent-agent/round-01/`에 있다. 기준 시각, 솔버 응답의 종료 시각, 같은 구간의 후보 공통 입력, 원본 해시를 대조했다. 시연 구간과 겹친 결과는 없었고 각 구간의 `case_group_id`는 서로 달랐다.

## 모의 판단 데이터

1차 수집 12개에 대해 AI가 스케줄러 역할로 **선택 4개, 보류 3개, 재계산 5개**를 기록했다. 2월 10일 파일럿을 포함한 총 13개는 `ai-judgments.json`에 있고, `ai-judgments.md`로 근거와 재검토 조건을 읽을 수 있다. 판단마다 후보 세트의 원본 해시, 화면 슬롯과 실제 배치 ID, 인용한 리스크 ID를 연결했다. 자료에서 확인할 수 없었던 예보·출하 마감·선석 변경 권한은 미확인으로 남겼다.

6개 구간은 팀 엔진으로 선석과 접안 순서를 고정해 재현했다. 각 비교에 동일한 풍속 정책을 적용하고 같은 선박에 ETA 3시간 지연과 하역시간 30% 연장을 각각 적용했다. 추가 비용과 후속 접안 지연은 `ai-review-replay.json`에 있다. 하역 연장 실험은 엔진의 유효 물량 조정 기능을 사용했으므로 이 실험으로 재고 영향을 판정하지 않는다.

모의 판단은 `ai_simulated_scheduler_review`로 기록했다. 개발용 유사 사례 검색과 보류·재계산 처리 검증에 사용할 수 있다. 운영 검색 노출은 검토 출처와 현장 확인 여부로 제어하며, 현재 운영 노출 대상은 0개다.

## 기본 설정으로 재현한 비교 사례

| 기준 날짜 | B 프리셋 | 배치 / 누락 | 예상 체선료 A / B / C | 실제 화면 배치 수 |
|---|---|---:|---|---:|
| 2025-05-07 | 보수적 풍속 기준 | 각 63 / 0 | USD 129,157.28 / 166,757.52 / 127,049.46 | 3 |
| 2025-07-27 | 안전재고 강화 | 각 67 / 0 | USD 102,721.99 / 102,721.99 / 138,282.78 | 2 |

- **5월 7일** A에서 C로 바꾸면 26건의 선석과 47건의 예정 접안 시각이 바뀌었다. 세 후보 상태는 `FEASIBLE`이다. A의 계획 비용과 솔버가 보고한 하한 차이가 커서, C의 계산값이 낮은 이유를 지연 여유 프리셋에만 돌릴 수 없다. 판단에 쓰려면 비용 비교 신뢰도와 당시 풍속 적용 기준을 먼저 확인한다.
- **7월 27일** 화면의 동점 규칙이 비용이 같은 A·B 가운데 탱크 하한 여유가 큰 B의 배치를 A 슬롯에도 표시했다. 실제 계산 배치는 세 종류였지만, 사용자가 비교한 화면 A·B는 같은 배치다. 원본 A와 B에서 `특수 반출` 최저 재고는 각각 24.1%, 25.9%이며 리스크 판정 하한 20%까지 여유는 4.1%p, 5.9%p다. 화면 슬롯과 원본 프리셋을 함께 저장해야 하는 사례다.

두 구간의 세 후보 모두 하역 속도 전처리 `168991ec2fb1`, 솔버 `2aa6a1b67390`, 리스크 `b94230c4092d`를 사용했다. 솔버의 연장 구간까지 시연 날짜와 겹치지 않았고, 사람의 판단과 현장 실행 결과는 공란이다.

## 탐색 한도에서 확인한 사례

- **4월 3일** 52건을 누락 없이 배치했지만, 세 안 모두 석유제품 반출 탱크에서 고정 상한 80%를 넘겨 최대 85.1%를 기록했다. 후보별 비용과 별개로 재고 이탈을 줄일 수 있는 조치가 있는지 검토해야 하는 구간이다.
- **6월 23일** 62건을 누락 없이 배치했다. 세 안의 예상 체선료는 USD 178,108.03으로 같고 배치는 달랐다. A와 B에는 탱크 하한 근접 경보가 있고 C에는 없다. 탱크 안전 범위 위반은 세 안 모두 0이다.
- **7월 7일** 48건을 누락 없이 배치했다. 세 안의 예상 체선료는 USD 14,286.66으로 같고 배치는 달랐다. B안은 풍속 기준을 낮췄으므로 A와 B의 기상 경보 수는 각자의 기준을 포함해 해석한다.
- **4월 19일** A가 탐색 한도 안에 계획을 반환하지 않아 A 결과가 필요한 B를 계산하지 않았다. C는 85건을 배치했고, 고정 상한 80%에 대해 최대 75.9%까지 올라가는 낮음 등급 경보를 냈다. 상한 접근 사례이며, 후보 선택 근거를 수집할 때는 A·B 재계산이 필요하다.

## 재현과 검토

기존 화면과 같은 방식으로 날짜별 하역 속도를 계산하고, A 결과로 B 프리셋을 고른 뒤 C와 함께 저장한다. 하역 속도에 사용할 과거 기록은 기준 시각까지 작업이 끝난 실적으로 제한한다. 모의 계획의 시간별 풍속은 사후 관측이며, ETA와 계약에 가정값이 포함된다. 화면과 같은 `rates: null` 리스크 요청을 사용하므로 하역 속도 근거 경보는 별도로 판정한다.

스냅숏에는 원본 요청·응답, 프리셋, 리스크, 배치 ID와 계산 상태를 남긴다. 배치 비교에서는 체선료 필드를 빼고 선석과 시각을 비교한다. 화면의 동점 표시 규칙이 적용된 결과도 별도로 남겨 실제 두 안이 같은지 확인할 수 있다. 솔버가 연장한 기간과 시연 기간이 겹친 결과는 수집 대상에서 제외한다. 사례 인덱스는 계산 구간이 겹치거나 같은 항차를 포함하는 경우 동일한 `case_group_id`를 부여한다.

### 실행

저장소 루트에서 팀 입력을 변환한 JSON, 팀 엔진 소스 경로, 해당 엔진 의존성이 설치된 Python을 지정한다. 결과 폴더를 준비한 뒤 날짜별로 실행한다.

```bash
node tools/real-data/capture_precedent_case.mjs \
  public/data/real-2025.json 2025-05-07 /path/to/round/2025-05-07.json \
  /path/to/team-engine /path/to/python
python3 tools/real-data/summarize_precedent_round.py /path/to/round
```

`--screening`은 첫 풀이 시간을 15초로 줄이고, 워커 수와 재풀이 횟수를 제한한다. 세 후보에 같은 한도를 적용하고 각 요청에 한도를 저장한다. `FEASIBLE`의 비용을 최적값으로 해석하지 않는다. 검토할 후보를 선정할 때는 목적함수 하한, 불필요 대기 수, 누락 건수를 확인한다. 전체 실행 시간에는 입력 준비, 재풀이, 리스크 계산도 포함된다.

### 판정에서 확인할 내용

- 탱크 경보는 상한과 하한을 구분하고, 입고·출고 조정이 각각 가능한지 확인한다. 재고 경보 수와 실제 제약 위반량은 따로 본다.
- 풍속 조건이 후보를 가르면 적용 부두, 당시 중단 기준, 그 시각에 받아볼 수 있었던 예보를 확인한다.
- 접안이 몰린 구간은 재배치로 어느 선박의 교대 여유가 바뀌는지 보고, 확정 마감과 이동 승인 여부를 확인한다.
- 동일 배치는 표시 슬롯과 프리셋이 달라도 실제 선석·시간을 먼저 비교한다. 미산출에는 솔버 상태와 원인을 저장하고, 보류는 검토자의 판단으로 기록한다. 검색에 해당하는 사례가 없는 상황은 이후 검색 검증 질의로 남긴다.

동일 배치와 계산 시간 제한에 따른 `NO_PLAN`은 합성 입력으로 별도 재현했다. `NO_PLAN` 검증은 모델이 정해진 시간 안에 배치를 반환하지 못했을 때의 처리에 쓰인다. 검색 결과가 비어야 하는 검증 질의는 탱크 상한 문제가 있지만 입고 지연 및 선석 이동이 모두 불가능한 상황이다. 해당 질의의 동작은 검색 구현 후 확인한다.
