# 유사 사례 에이전트 초기안 대조

[실행 로드맵](precedent-agent-roadmap.md) / [데이터 정의](precedent-agent-data.md) / [초기 기획안](https://chatgpt.com/library?file_id=libfile_74aaf392182481918bd785a8d0c8b063&account_id=personal)

대화의 최초 목표는 실제 팀 솔버의 A/B/C 후보를 비교한 이유를 기록하고, 이후 비슷한 상황에서 적용 조건과 감수한 대가를 찾는 것이다. 현재 구현은 이 흐름을 따른다. 가장 큰 변경은 사용자가 판정을 맡기기로 한 뒤 사람의 독립 검토를 AI 모의 판단과 별도 수치 검증으로 바꾼 것이다.

| 초기 요청 | 현재 확인 | 남은 범위 |
|---|---|---|
| Notion 데이터와 팀 솔버로 3일씩 실행하고 시연 4개 날짜 제외 | [R11 추가 수집](precedent-agent-round-03.md)에서 설비 중단 3개, 긴급 출하 2개, 고정 접안 3개를 보강했다. 현재 29개 구간 중 19개에 A/B/C와 리스크가 있다. 시연·연장 구간 겹침을 검사했고 항차·시간 기준으로 17개 그룹에 묶었다. | 추가한 조건은 실적 입력에 적용한 모의 조건이다. 실제 현장 제약 원본이나 당시 결정 근거는 입수 시 별도로 연결한다. |
| 세 후보의 정보, 리스크, 선택 및 근거 저장 | 원본 실행에는 세 후보의 입력·프리셋·배치·리스크·미산출, 모델 버전이 연결된다. 모의 판정에는 선택·보류·재계산과 경합안, 근거, 재검토 조건이 있다. R08에서는 화면 확정에서 후보 세 개와 참고 사례를 별도 판단 기록에 연결한다. | 팀 공용 저장 및 실제 사후 결과 연결은 별도 운영 범위다. 지금 화면 기록은 브라우저에 남는다. |
| 유사 조건이 무엇인지 정의하고 화면에서 적용 여부 설명 | R07에서 탱크 방향과 한계, 교대 여유, 체선 임박 상태, 풍속 기준, 후보 미산출을 구조화했다. [R12](precedent-agent-r12.md)에서 설비 중단, 긴급 출하, 고정 접안도 계획 입력에 연결했다. 적용할 수 없는 과거 조치와 미래·동일 그룹·평가 사례를 제외한다. | 복수 제약이 동시에 충돌하는 사례는 제약 하나를 골라 조회한 뒤 나머지 조건을 함께 확인한다. 실제 변경 권한·당시 예보·확정 마감은 모의 입력과 별도로 확인해야 한다. |
| 과거에 자주 고른 안을 보여주는 것의 업무 효과를 점검 | 선택 빈도는 검색 정렬에 쓰지 않는다. [R09 모의 검증](precedent-agent-effect.md)에서 같은 데이터의 태그 검색은 적합 사례 1건, 제약 기반 검색은 6건을 반환했다. 이후 [R10 화면 보강](precedent-agent-screen.md)에서 사례가 없는 탱크 제약의 확인 사항과 후보 미산출 시 재계산 근거를 표시했다. | 실무 효과는 실행·정산 자료와 사람 판단 소요시간을 확보한 뒤 평가한다. |
| 필요한 데이터 정의, 파이프라인 시각화, 실행 로드맵, 완료 체크 | 데이터 정의와 Mermaid 파이프라인, 완료 근거를 연결하는 체크 명령을 저장소에 작성했다. | 검색 코퍼스와 화면 판단 기록을 다음 수집에 합칠 때는 동일 항차 그룹과 판정 출처를 유지해야 한다. |
| 기업의 숙련자 지식 형식화 사례 검토 | 초기안에 Toyota A3, BP의 Peer Assist/AAR, Critical Decision Method, 벌크 터미널 지연 재현 연구가 있다. 경합안과 판단 단서, 당시 근거와 사후 결과 구분, 공통 교란 검증에 반영했다. | 실제 결정 당시의 업무 기록이나 현장 실행 결과는 현재 모의 판단에서 미확인이다. |

첫 파일럿 선정 때 확인한 약 37시간 정박지 대기를 해소했다는 결과는 현재 산출물에서 확인되지 않는다. 그 대기시간은 관제 관측값으로 보존한다. 원천 항차의 정확한 매칭과 비교 가능한 실제 실행 기록이 있으면 당시 대기 원인과 대안별 운영 영향을 별도로 검증할 수 있다.

현재 리스크 API 요청은 기존 화면 경로와 동일하게 전처리 속도 근거를 별도로 보내지 않는다. 하역 속도 산출 자료는 원본 스냅숏에 있지만 `RATE_BASIS` 리스크 적용은 별도 검증이 필요하다.

제품 검증에서 우선 확인할 대목은 **검색이 보여준 조치가 실제로 이번 안에서 가능한가**, **그 조건이 바뀔 때 어떤 후보가 탈락하는가**, **근거 없이 확정하는 사례가 늘지 않는가**다. 추가 수집은 검색 정확도와 업무 판단에 필요한 빈 조건을 메우는 데 사용한다.
