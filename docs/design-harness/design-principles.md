# D-MIN 계정 관리 설계 원칙

범위는 Figma `1004:1448` 관리자 섹션과 `?view=admin`이다. 로그인·회원가입·운영·계획·메일 화면은 탐색과 회귀 확인만 하며 수정하지 않는다. 의존성·lock·빌드 설정은 변경하지 않는다.

## 작업 맥락

운영 담당자의 이름·사번을 식별하고 담당 부두·팀과 요청 역할을 검토한 뒤 접근 상태를 관리한다. 스케줄러는 계획 작성·비교·확정 권한 때문에 팀장 승인 확인이 필요하다. 계정의 승인 이력과 현재 활성 상태는 서로 다른 정보다.

## 설계 방향 비교 — 구현 전 결정

| 방향 | 정보 구조와 업무 흐름 | 밀도·표현 | 적합성·한계 |
|---|---|---|---|
| A. 운영 대장 + 검토 패널 | 상태로 대상을 좁히고 목록에서 비교, 옆 패널에서 검토·처리 | 정렬된 표, 중립적 경계, 상태·행동만 강조 | 반복적인 다수 계정 비교에 적합. 좁은 화면은 별도 상세 전환 필요 |
| B. 신청함 + 단일 검토 화면 | 한 신청을 열고 다음 신청으로 이동 | 큰 본문, 순차적인 확인 항목, 단일 열 | 한 건 집중 검토·모바일에 유리하나 여러 소속·역할 비교와 기존 계정 관리의 이동 비용이 큼 |
| C. 역할·소속별 권한 작업대 | 역할/팀을 먼저 고른 뒤 대상 계정 관리 | 역할별 목록·범위 행렬 중심 | 대규모 권한 개편에는 유리하나 현재 두 역할과 승인 업무에는 탐색 단계가 늘고 실데이터 없는 행렬을 만들 위험 |

**A 선택.** 업무 목적이 역할 제도 설계보다 신청 검토와 기존 계정 관리다. 좁은 화면에서는 목록의 이름·소속·상태를 함께 보이고 선택한 상세를 모달 검토 패널로 연다. 패널과 목록 사이의 왕복을 줄인다. 외부 제품 UI를 복제하지 않으며, 이번 결정에서 확인하지 않은 외부 레퍼런스를 분석했다고 주장하지 않는다.

## 디자인 규칙

- Pretendard는 기존 제품 글꼴을 사용한다. 본문 14px, 보조 12px 이상, 제목 24px. Figma에서 Pretendard를 사용할 수 없다면 Noto Sans KR 대체를 명시한다.
- 브랜드 빨강은 선택 지시와 주요 동작에 제한한다. 승인/정상은 녹색, 미확인은 중립/주의, 반려·비활성화는 명확한 텍스트와 확인 절차로 구분한다.
- 간격 4/8/12/16/24/32px, 경계 1px, 기본 반경 4px. 부품마다 다른 반경과 카드 중첩을 만들지 않는다.
- 상태·확인 라벨은 실제 값에 따라 달라야 한다. 이력이 없으면 없다고 표시한다. 발송되지 않은 메일을 발송 완료로 표현하지 않는다.
- 기능의 이유가 설명되는 아이콘만 유지한다. 이름 이니셜은 사진이나 계정 정보의 대체 데이터가 아니다.
- 표, 검토 패널, 모달은 같은 색·타이포·컨트롤 규칙을 사용한다. 화면별 데이터 구조와 목적은 보존한다.
- 1920×1080, 1440×900, 1280×800, 768×1024, 390×844에서 실제 렌더링한다. 모바일은 단순 축소 대신 필요한 정보와 처리를 연결한다.

## 재실행

개발 서버를 실행한 뒤 `node scripts/design-qa/capture.mjs <label>`을 실행한다. Chrome은 `CHROME_BIN`, 서버는 `DESIGN_QA_URL`로 지정할 수 있다. 의존성 설치 없이 임시 프로필을 사용하며 사용자 브라우저 데이터에 접근하지 않는다.

계정 데이터는 기존 브라우저 시연 저장소에 있다. 서버에 연결된 실계정이 없다는 사실을 숨기거나 새 가짜 계정·통계·감사 기록을 추가하지 않는다. QA만 시계를 고정하며 동일한 기존 초기 데이터로 비교한다.
