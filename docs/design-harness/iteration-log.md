# 반복 개선 이력

평가표는 `evaluation-rubric.md`로 고정했다. 각 단계는 실제 코드를 수정하고 실제 브라우저에서 렌더링한 결과다. 구현량이나 의도는 점수 근거에서 제외했다.

## 역할 분리

- Principal Product Designer: 주 에이전트의 감사·세 방향 비교·정보 구조 결정 단계.
- Senior Design Engineer: 주 에이전트의 구현·렌더링·기능 검증 단계.
- Independent Design Critic: 구현하지 않은 별도 `design_critic` 에이전트. PNG·코드·검증 기록으로 평가. 인간 외부 평가나 실고객 승인이 아니다.
- Enterprise Acceptance Reviewer: 별도 `acceptance_review` 에이전트. 상태·감사 기록·손상 데이터·범위·검증의 타당성 점검. 읽기 전용으로 코드와 증거를 보고 격리 단위테스트를 실행했다.

## Iteration 0 — 62/100 / 기준 고정

- 관찰: 1920/1440/1280/768/390 요청·계정, 주요 모달·빈 상태 16개 캡처.
- 원인: 지표 카드·중복 헤더·화면별 미세 스타일, 식별 정보를 낮춘 글자 크기, 모바일 표 축소, 업무 상태와 표현의 혼용.
- 감사: `baseline-audit.md`. 고정 데이터 12개와 QA 시계를 사용했다.
- 증거 주의: 최초 캡처의 모달 3개가 진입 애니메이션 중이었다. 평가자는 이를 제품 결함으로 계산하지 않았고, 유한 애니메이션 종료 후 Baseline을 재촬영했다.

## Iteration 1 — 76/100 / 전체 후보 폐기

- 가설: 반복 지표·헤더·장식을 덜고 목록과 검토 패널을 통일하면 식별과 비교가 빨라진다.
- 구현: 중복 masthead와 세 지표 카드, 이니셜 아바타·역할 pill 제거. 본문 14/보조 12px, 의미 색·단색 CTA·파란 초점. 공통 FilterBar/Pagination/AccountPanel/CheckItem. 페이지당 10건으로 기존 6건을 함께 표시.
- 관찰: 데스크톱 위계·대비·밀도는 개선됐으나 모바일 CSS의 `span` 선택자가 Blueprint 아이콘까지 숨기는 **신규 Major** 발생. 이력 화면의 빈 열도 확인.
- 판정: 전체 채택 조건 미충족. 두 UI 파일을 기준 커밋 상태로 실제 복귀한 뒤 다음 가설로 진행했다. 사용자 변경 파일은 복귀 대상에 없었다.
- 증거: `evidence/iteration-1/`. 점수를 올려 채택하지 않았다.

## Iteration 2 — 83/100 / 다음 개선의 기준 버전 채택

- 가설: 작은 화면에서 표를 자르기보다 이름·사번·역할·소속·상태를 함께 제시하고, 선택 즉시 상세 검토로 연결해야 한다.
- 구현: 1100px 이하 핵심 정보 목록 + 상세 Dialog + 권한 변경 Dialog. 메뉴의 텍스트/아이콘 선택자 분리와 명시적 접근 이름. 태블릿 밀도와 이력 단일열 수정.
- 실제 검증 중 발견: 조건부 언마운트 때문에 `onClosed`가 호출되지 않아 중첩 모달 초점 복귀가 완료되지 않았다. 열린 상태와 보존 데이터를 분리해 닫기 수명주기를 유지하고 `onOpened` 초기 초점·명시적 트리거 복귀로 수정했다.
- 검증 도구 문제도 구분: 초기 CDP Enter 이벤트의 문자 정보와 창 초점이 불완전했다. 실제 키 입력 전송과 레이아웃 안정화 대기를 바로잡았다. 제품 문제와 도구 문제를 섞어 성공 처리하지 않았다.
- 판정: 19개 PNG, 10개 브라우저 체크에서 새 Major 없이 개선 확인. 승인 집계·감사 fallback·메일 문구는 다음 단계로 남겼다.

## Iteration 3 — 89/100 / 개선 후보 채택, 납품 보류

- 가설: 관리 화면의 품질은 상태·기록·오류 표현의 사실성과 실패 후 작업 보존에서 결정된다.
- 구현: 승인 완료에 활성/비활성 모두 포함. 실제 변경 이벤트가 없으면 없다고 표시. 확인 전 승인 비활성화. 메일 안내 요청 기록과 실제 미연동 구분. 검색 초기화, 저장 실패 입력 보존·재시도, 손상 원본 보존, 이전 확인창으로 다른 창의 상태를 덮지 않는 방어.
- 근거: 실제 22개 상태 캡처와 별도 키보드 복귀 캡처, 브라우저 18개 체크, 텍스트 대비 실패 없음. 당시 단위테스트 7개 통과.
- 판정: 90점 기준 미달. 남은 당일 집계 의미, 모바일 필터 축약, 읽기 실패를 0으로 보이는 표현을 다음 단계 대상으로 삼았다.
- 별도 수락 검수에서 추가 발견: 공용 폼 기본 반려 사유와 숨은 메일 요청이 다른 처리 이력에 섞임. 저장된 문자열 `"false"`가 정상 확인값처럼 수락됨. Baseline부터 있던 결함이지만, 앞선 통과 결과가 이를 검증한 것은 아니었다. 추가 Major로 기록하고 완료하지 않았다.

## Iteration 4 — 91/100 / 최종 채택

- 가설: 처리별 입력과 저장 경계를 모두 제한하고, 역할·담당 부두·팀을 우선 검토 단위로 배치하면 업무 판단과 기록의 신뢰성이 개선된다.
- 구현: 승인/반려/권한/활성 상태별 입력 분리와 감사 detail/notify 제한. 실제 boolean `true`만 승인에 사용. 정상 JSON 내부의 잘못된 boolean·표시 필드·중복 ID도 차단하며 원본 보존. 당일 접수 총량은 상태와 무관하게 계산. 읽기 실패는 `—`와 확인 불가로 구분. 모바일 필터 전폭 확보. 이름 직후에 역할·운영 담당 범위 배치.
- 검증: 최종 단위 10/10, 필수 브라우저 체크 18/18, 계산된 가시 텍스트 59개·70개에서 대비 실패 0, 12px 미만 0. 다섯 화면 크기와 23개 상태 캡처. 신규 오류 0(기존 favicon 404 별도).
- 독립 판정: 디자인 리뷰 **91/100**, 수락 리뷰의 이전 Major A/B 해결, 관리자 UI 범위의 미해결 Critical/Major 0.
- 남은 Minor: 빈 결과/읽기 실패의 페이지 ‘1’ 표시, 모바일 행의 외부 초점선 일부 잘림. 필수 작업은 가능하며 문서에 남겼다.
- 사용자가 이후 “필수 테스트만” 요청한 뒤에는 이미 통과한 기능 검사를 반복하지 않았다. 새로 작성한 Figma의 구조·잘림, 의존성/범위 보존과 결과 기록만 확인했다. 최종 제품 코드의 기존 성공 빌드 로그를 보존했다.

## 재현 조건과 한계

`evidence/fixture-integrity.json`은 기준 커밋과 최종 코드의 초기 계정·이력 레코드가 동일함을 확인한다. 당일 집계 6→12는 데이터 추가가 아니라 대기 건만 세던 의미를 전체 당일 접수로 바로잡은 결과다. 각 단계의 `accountRecordHash`는 동일한 레코드 해시다. 초기 `fixtureHash`는 저장소 건강 메타데이터까지 포함한 구형 방식이므로 레코드 비교에는 사용하지 않는다.

평가 순서를 가리는 블라인드 평가는 실시하지 않았다. 점수는 고정 루브릭의 별도 에이전트 판단이며 자동 검사 점수나 실고객 만족도 측정값이 아니다. 운영 납품 승인은 서버·조직 정책·실사용자 검수와 함께 별도로 판단해야 한다.
